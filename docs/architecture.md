# SeatFlow 总体架构

SeatFlow 采用[模块化单体](decisions/0001-modular-monolith.md)。应用由一个 Go 进程提供 HTTP 服务，MySQL 独立运行并保存持久化数据。

## 目录与职责

| 路径 | 职责 |
| --- | --- |
| `cmd/server` | 装配配置、数据库连接和 HTTP 路由，启动服务 |
| `internal/config` | 从进程环境读取 HTTP 监听地址和可选的 MySQL 连接配置 |
| `internal/handler` | 处理 HTTP 请求并生成响应，目前提供健康检查 |
| `internal/service` | 承载后续业务规则并协调事务边界 |
| `internal/repository` | 初始化数据库连接并承载后续持久化操作 |
| `internal/model` | 定义后续业务实体和数据结构 |
| `migrations` | 存放版本化数据库迁移 |
| `tests` | 存放跨包集成测试。包内测试与对应代码放在一起 |
| `deployments` | 存放本地 MySQL 的 Compose 配置 |
| `docs/decisions`、`docs/milestones` | 记录架构决策和阶段交付范围 |

预留目录随首个实际文件纳入 Git。后续业务请求由处理器调用服务层，服务层协调仓储操作，并持有跨操作的事务边界。业务实体由模型层定义。

## 运行边界

`GET /healthz` 返回 HTTP 200 和 `{"status":"ok"}`，表示 HTTP 服务可响应。设置 `MYSQL_DSN` 后，应用会在监听前通过 GORM 初始化 MySQL 连接，连接失败时退出。MySQL 容器使用应用账号查询 `SELECT 1` 来检查数据库健康状态。

## 数据一致性原则

以下约束适用于后续票务实现。

- MySQL 是座位归属与订单状态的最终事实来源。关键不变量由数据库唯一约束、条件更新及受影响行数检查共同维护。
- 同一场次的同一座位最多由一个有效订单占用。多座位预订在同一事务内全部成功或全部回滚。
- 涉及多个座位的事务使用稳定的加锁顺序。实现须说明事务隔离级别和锁行为，并处理死锁及锁等待超时。
- 有副作用的重试依赖幂等机制和明确的重试上限。过期释放须校验当前占用归属与状态。
- 数据库结构变更通过版本化迁移管理。事务、行锁及并发竞争的验收使用真实 MySQL。
